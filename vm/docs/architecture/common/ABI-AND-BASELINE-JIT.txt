QuickJS-Turbo ABI Contract & Proposed Baseline JIT Architecture
===============================================================
Updated: 2026-11-26 (v0.17.0-turbo.3 / QuickJS-NG 0.17.0 verified baseline)

Status Note
-----------
QuickJS-Turbo `v0.17.0-turbo.3` ships exclusively as a **Zero-JIT, `0 RWX`
register-frame assembly interpreter** (Section 1). Section 2 documents a
**proposed future roadmap** for an optional, opt-in bytecode-driven Baseline
JIT built on top of the shipping ABI; no runtime code generation is present in
`v0.17.0-turbo.3`.

1. Two-Layer ABI Contract (Shipping Production Invariant)
---------------------------------------------------------
QuickJS-Turbo enforces a strict separation between the public embedder ABI and
the internal register-frame execution ABI:

1.1 Public C & Bytecode Wire ABI (100% Drop-In)
- Upstream QuickJS-NG `0.17.0` (`quickjs.h`, `quickjs-libc.h`, `BC_VERSION 29`)
  remains byte-for-byte unmodified at the repository root.
- Zero changes to public struct sizes, `JSValue` representation (`16 B`, tag at
  offset `8`), or `JSRuntime`/`JSContext` public API semantics.
- Verified drop-in compatibility with unmodified `txiki.js v26.11.0` (`5133e8a`)
  and full `82,220`-case Test262 (`0` new regressions).
- All Turbo-specific controls (`quickjs-turbo.h`: `QJS_TurboOptionsInit`,
  `QJS_SetTurboDefaults`, `JS_SetRuntimeTurboOptions`, `JS_PurgePropertyIC`,
  `QJS_GetTurboInfo`) are strictly additive.

1.2 Internal Native Register-Frame ABI (Shipping Execution Substrate)
- Pinned hardware register contracts across tier-1 native backends:
  - `LINUX_AARCH64` (`vm/asm/arm64/linux/interpreter.S`):
    `x19` `JSFrameRegisterState*`, `x20` bytecode `pc`, `x21` operand `sp`,
    `x22` `JSStackFrame*`, `x23` `var_buf` (locals), `x24` `arg_buf` (args),
    `x25` relative dispatch table; `JS_FrameInterp` strictly 64B-aligned
    (`161` native opcodes, PIE, NX stack, `0 RWX`, full DWARF FDE coverage).
  - `LINUX_X86_64` / `MACOS_X86_64` / `WIN_X86_64`:
    Equivalent callee-saved register pinning over the shared `JSFrame` segment
    arena, with SysV/Mach-O DWARF CFI and Win64 SEH `.pdata`/`.xdata` unwind
    metadata.
- Bounded bytecode admission (`FRAME_KIND(b)` + jump-target `boundaries` bitmap):
  Pre-validates stack bounds, arity, and branch targets per `JSFunctionBytecode`
  before entering native execution.
- Clean/Dirty lazy stack-frame publication (`publication_release.py`):
  Fast-path instructions execute without committing `cur_pc`/`cur_sp` until an
  observing boundary (C helper, JS call, GC safepoint, exception, or finalizer).
- Build-time ABI verification:
  `core-fields.json` and `511` SHA-256 source/ABI receipts (`contracts.py`,
  `test_arch_boundaries.py`, `validate_layout.py`, `check_vm.py`) fail closed
  on any offset or layout drift.

2. Proposed Optional Bytecode-Driven Baseline JIT (Future Roadmap)
------------------------------------------------------------------
Symbol-level hardware sampling (`perf` on AWS Graviton2 Neoverse-N1 and Linux
x86-64) records `53%–98%` of self-samples inside `JS_FrameInterp` across
compute and object workloads (`crypto`, `richards`, `delta-blue`, `acorn-wtb`,
`Babylon`). While symbol-level sampling alone does not separate removable
dispatch/decode overhead from intrinsic object/arithmetic work, an optional
Baseline JIT tier is designed to directly target three interpreter costs:
1. Per-opcode indirect branch dispatch (`ldrb + ldrsw + add + br` / `jmp *table`);
2. Dynamic bytecode operand fetch/decode and `pc` register increments;
3. Stack-machine `[sp]` memory traffic (`16 B` `JSValue` push/pop & repeated tag
   checks within basic blocks).

2.1 Why No AST Would Be Added
- QuickJS is a single-pass bytecode compiler (`quickjs.c` -> `JSFunctionBytecode`
  + `compiler-plan.c` TDZ compaction). Introducing an AST would break the
  `96.29 KiB` (`98,600 B`) initial runtime+context heap invariant and sub-ms
  parse latency.
- Industry Baseline JITs (V8 Sparkplug, JSC Baseline, SpiderMonkey Baseline,
  CPython Copy-and-Patch) compile directly from bytecode: lexical scopes,
  captured `JSVarRef`s, TDZ, jump labels, and exception tables are already
  lowered, and OSR / bailout / `pc2line` / IC indexing all require 1:1 `pc`
  alignment.

2.2 Proposed Architecture Over the Existing Register-Frame ABI
- Proposed Compilation Backend: Offline-verified Copy-and-Patch machine-code
  stencils (reusing the `vm/tools/{x86,arm64}` build/verify pipeline) paired
  with a **1-pass basic-block virtual operand stack** (2–4 register TOS cache +
  local tag tracking using the existing `boundaries` bitmap to detect block
  merges).
- Proposed Zero-Bridge ABI Sharing:
  - JIT frames would reuse the exact `JSFrame` arena and callee-saved register
    contract of `JS_FrameInterp` so `JIT <-> Interpreter` calls need no adapter
    frame.
  - Fast paths would free `pc` (`x20`) and `dispatch_table` (`x25`); cold
    bailout stubs would materialize the compile-time constant `pc` and jump
    into existing Clean/Dirty slow paths and C helpers.
- Proposed Direct-Baked Property ICs & Monomorphic Calls:
  - Per-site IC slot pointers would be encoded PC/RIP-relatively inside JIT
    code, falling back to `fast-get-field.inc` on miss.
  - Guarded monomorphic `OP_call` / self-recursion direct branches.
- Proposed Hotness Tier-Up, Loop OSR & Strict `W^X` Governance:
  - Default production mode remains **Zero JIT / `0 RWX`** (opt-in via compile
    and runtime switches so iOS, consoles, and `no-WX` sandboxes stay unaffected).
  - Per-`JSFunctionBytecode` hotness counter (entry + backedge, e.g. threshold
    64–128) keeps cold scripts and startup code at `0 B` JIT memory.
  - Per-function `{pc_offset -> native_loop_entry}` table would support Loop OSR
    from the interpreter on long first-run loops.
  - Bounded per-`JSRuntime` Code Arena (e.g. 8 MiB cap) would enforce strict
    `W^X` (`PROT_READ|PROT_WRITE` during emit -> `PROT_READ|PROT_EXEC` on
    publish; never simultaneous `RWX`), embed no untracked `JSObject*` GC roots
    (compatible with `hybrid-gc.inc`), and safely evict cold blocks under
    memory pressure.

2.3 Phased Validation & Stopping Criteria
- Phase 0 (Single-Arch PoC, ~35–45 core arithmetic/local/branch opcodes + OSR):
  Compile time `< 100 us/fn`; must achieve `>= 1.35x` on compute/branch loops
  (`crypto`, `navier-stokes`, `bitops`) before expanding opcode coverage.
- Phase 1 (Direct-Baked Property ICs + Fast Dense/TypedArray + Monomorphic Call):
  Target `>= 30%–60%` V8-v7 uplift and `>= 20%` JetStream-17 body reduction
  with `<= 1%` cold/first-iteration regression.
- Phase 2 (Dual-Arch `LINUX_X86_64` + `LINUX_AARCH64` Alignment & Hardening):
  Architecture DAG check (`test_arch_boundaries.py`), `.eh_frame` / `perf.map`
  registration, OOM/eviction stress, `96.29 KiB` cold-heap parity, and full
  `82,220`-case Test262 (`0` new regressions under forced threshold=1 + eviction).
